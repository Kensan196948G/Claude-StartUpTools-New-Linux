# Ship 署名の誤操作防止：影響分析とロールバック（R4）

対象は #238 マージ後の main（`8e5d3de`）を基点とする `ship-attest` の CLI 変更。レビュー中に残った修正を取り込む前の署名と、重大な指摘の件数の転記ミスを防ぐ。署名の正当性を判定する既存のゲートは置き換えない。

## 1. 影響分析

PR 全体のリスクは R4。R4 に分類される `bin/ship-approve.sh` と署名経路を変更するため、ローカル品質検証、`/ship`、対象 SHA の署名、品質判定、人間の最終承認を通す。

| 対象 | 変更と影響 | 確認方法 |
| --- | --- | --- |
| `/ship` 結果の署名（既定または `--kind ship`） | `--workdir DIR` が必須。指定した Git 作業フォルダの `HEAD` と署名対象 SHA が一致し、Git が未コミットの変更・未追跡ファイルを報告しないことを確認する。`--reviewed yes` の場合は対象を端末に示し、未解決の重大な指摘の件数を入力し直す | `lifecycle.test.js`：引数なし、Git 外、違う SHA、追跡・ステージ済み・未追跡の変更、件数違い、正常時の署名と監査を確認 |
| 利用者向け手順 | `bin/ship-mode.sh` の案内、`bin/ship-approve.sh --help`、運用手順書を更新。旧手順のコマンドは `--workdir` を補うまで停止する | シェル構文、ヘルプに `--workdir` と `human-diff` の案内があること、手順の整合を確認 |
| R0・R1 の `--kind human-diff` | 新しい引数や件数の再入力は不要。既存の確認画面、署名、適用リスクは変えない | `lifecycle.test.js` の既存テストで差分確認・R2 拒否を確認 |
| 署名、品質判定、最終承認 | 署名形式 v1/v2、鍵、信頼ポリシー、品質判定、マージ条件は変更しない。既存の署名は従来の条件で検証される | 既存のライフサイクル・署名検証テストで回帰を確認 |
| 監査・運用基盤 | `/ship` の `ship_attested` 監査イベントに作業フォルダの確認結果と再入力の有無を追加。フォルダのパスと端末入力そのものは監査イベントに記録しない。DB スキーマ、GitHub ruleset、中央ポリシー、実行権限は変更しない | 監査の追加項目をライフサイクルテストで照合 |

### 前提と残る制約

- 利用者が `/ship` を実行したフォルダと、GitHub 上でレビューした head SHA を指定することが前提。CLI はレビュー結果の原文を読まず、`/ship` 実行の事実や件数の正しさは証明できない。Git が無視するファイルは検査対象外だが、確認画面に件数と例を表示し、監査ログ（`workdir_ignored_count`）に件数を残す。練習用 clone が `.git/info/exclude` で生成物を除外する運用を妨げないよう、拒否はしない。監査ログの `important_retyped` は端末での入力時だけ `true` とし、入力元は `important_input_source` に残す。
- 作業フォルダは端末入力前と入力後に確認する。Git が認識したルートを端末に示し、状態確認の前後で `HEAD` を照合する。並行操作をロックするものではない。レビューから署名まで同じフォルダで別の操作をせず、別の SHA に変わった場合は再レビューする。
- 検査は信頼済みの実行環境（Git 2.38.0 以上）と、利用者が管理する通常の Linux 上の SHA-1 Git 作業フォルダ・Git メタデータが前提。検査用 Git ではトレース出力を無効にする。追跡ファイルに適用される外部 `clean` / `process`、サブモジュール、変更を隠し得るインデックス状態を検出したら中止する。未使用の Git LFS 等の設定は拒否しない。
- 署名用の検査では `git status` を呼ばず、対象コミット・インデックス・ディスク上のバイト列とファイル種別を照合する。外部フィルターだけでなく、改行や文字コードなどを Git が変換して初めて一致する作業フォルダも検査を通らない。Git の警告・失敗・処理ごとの 10 秒／32 MiB の上限超過は理由を示して中止する。警告の診断は端末用に短く整形し、既知の秘密情報パターンをマスクする。
- Linux の通常の行入力を使い、長すぎる件数入力は1行を読み取ってから拒否する。行が確定していない場合、または通常の行入力ができない端末でもパスフレーズ入力に進まない。
- テストは一時リポジトリとテスト専用鍵を使用する。実機の正式な署名・承認は人が端末で行う。検証機能のない旧 CLI では新しい安全装置は働かないため、適用後は main を更新して使う。

## 2. ロールバック手順

1. マージ済みコミットを GitHub で確認し、最新の main から切り戻しブランチを作る。squash マージされたこの PR の全体を `git revert <マージコミットのSHA>` で戻す。コードだけ、手順書だけの部分的な切り戻しはしない。
2. 切り戻しも R4 の PR として扱う。ローカル品質検証、`/ship`、対象版の署名、品質判定、最終承認を経るまでマージしない。切り戻し PR の署名は、その時点で main 上にある CLI と手順を使う。
3. マージ後、`bash bin/ship-approve.sh --help` が旧手順に戻り、`node --test scripts/ship/test/*.test.js` が通ることを確認する。`human-diff` と最終承認の挙動は変更されない。
4. 署名・監査ログ・鍵は削除も書換えもしない。切り戻し後は、利用者が署名前にレビューした SHA・作業フォルダ・未解決件数を手動で照合する。既存の SHA 不一致・品質不足を拒否するルールは維持する。
