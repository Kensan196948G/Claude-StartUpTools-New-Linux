# verification-loop

## 概要

この skill は 手動チェックをスキル化した検証ループ（検出 → 修正 → 再実行）を設計・運用する ための実務向けガイドです。
Anthropic 公式ガイド [Building verification loops in Claude Code with skills](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills) (2026-07-22) に準拠します。

## 使う場面

- 実装後に毎回手で行っているチェックを自動化された検証ループへ変換したいとき
- 変更を「実装しただけ」で終わらせず、全チェック PASS まで反復させたいとき
- 複数スキルをチェーン化して開発サイクル全体（実装 → 整理 → 検証 → デザイン確認）を自律化したいとき

## 想定入力

- 対象となるコード、差分、テスト結果、ビルドログ
- 毎回手で行っている確認手順（平易な文章で書き出したもの）
- プロジェクトの検証コマンド（CLAUDE.md 記載が最優先。なければ manifest から推定）

## 期待する出力

- 全チェックの PASS / FAIL / BLOCKED / NOT RUN 一覧
- 失敗 → 修正 → 再実行の履歴と、修正しきれなかった項目の原因分析
- 再利用可能な検証スキル（`.claude/skills/<name>/SKILL.md`）

## 検証ループの4つの起動形態

| 形態 | 発火タイミング | 使いどころ |
|---|---|---|
| standalone | 手動または明示的な呼び出し | 単独で回す検証。チェーン化前の試運転にも使う |
| embedded | 生成系スキルの末尾に組み込み | 特定ワークフロー専属のチェック（例: scaffold 後に lint） |
| chained | あるスキルが終了時に次のスキルを呼ぶ | 開発サイクル全体の自律化（実装 → /simplify → /verify → デザイン確認） |
| on every PR | PR 作成・push 時（CI / Code Review） | チームインフラ化。チェーンが安定してから導入する |

## 標準手順

1. まず既存の検証手段を確認する（toolchain のエラー、既存テスト、lint、CLAUDE.md の検証コマンド）
2. 毎回手で行っているチェックを 1 つ選び、新しいチームメイトへ渡すつもりで平易な文章に書き出す
3. `.claude/skills/<name>/SKILL.md` として frontmatter（name / description）付きで作成する
   - description には「何をするか」と「いつ使うか」の両方を書く
   - flat な .md はスキルとして認識されない（ディレクトリ + SKILL.md 形式が必須）
4. 新しいタスクで発動させ、チェックが出力に含まれることを確認する（含まれなければ description を改善）
5. 検出 → 修正 → 再実行のループ規則と修正回数上限（例: 3 回で BLOCKED）を明記する
6. 安定したら embedded / chained 化し、さらに安定したら PR ゲートへ昇格させる

## 詳細ガイド

### 設計時に確認すること

- チェックは決定論的か（同じ入力で同じ判定になるか）。定性的なら判定基準を rubric として明文化する
- プロジェクト固有ルールこそスキル化の価値が高い（例:「column を drop する migration は backfill 手順必須」は汎用 linter では検出できない）
- ループの終了条件（全 PASS / 修正上限 / BLOCKED 判定）が明確か

### 実装時に確認すること

- 検証コマンドを推測に頼らせず、CLAUDE.md またはスキル本文へ明記しているか
- 失敗時に「該当チェックのみ再実行」できる粒度でチェックを分割しているか
- 実行できないチェックを成功扱いにせず NOT RUN として報告する規則があるか

### 検証時に確認すること

- スキルを発動した新規タスクで、チェックが実際に出力へ含まれるか
- チェーン化した場合のトークン消費が許容範囲か（チェーンは柔軟性と引き換えに自動化を得る）
- PR ゲート化はチェーンが安定してからか（調整のたびにチーム全体へ影響するため）

## 相性のよい command

`/verify`, `/verify-app`, `/verify-startuptools`, `/design-sync-check`, `/safe-auto-merge`

## 相性のよい agents

`loop-operator`, `qa-agent`

## 注意点

- この skill は実装を急がせるためではなく、失敗率を下げるために使う
- 外部状態が読めない場合は推測せず、その前提を明示する
- チェーン化はトークン消費を増やす。広く展開する前に単体で試験する
- ステップを単独でも実行したい場合はチェーン化しない（柔軟性と自動化のトレードオフ）
